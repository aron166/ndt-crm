## The four concepts you're under-reflecting

### 1. Person is permanent, employment is a state
You have Person ≠ Contact. Good. Check that the schema also has:
- **Employment** as a first-class, time-bounded entity: `(person_id, company_id, role, valid_from, valid_to)` — `valid_to` nullable for current job, multiple historical rows allowed.
- **Versioned contact data**: a person's email/phone/title can change over time. Either an `employment_contact_data` JSONB on the employment row, or a separate `person_contact_versions` table. **Reason:** when looking back at a 2023 conversation thread, the email at the time must be reconstructable.
- **Unified communication history per person**: all interactions roll up to the person, regardless of which company they worked at when the interaction happened.

Test: "Kovács Béla worked at Company A 2020–2023, now at Company B." The person detail page should show his complete history, his 2021 emails should still link to him, and Company A's page should still show him in its historical employee timeline. If your current code can't do that, that's a schema gap.

### 2. Tasks are microtasks with executor + cost attributes
Your current Task model has subtasks, estimated vs actual minutes, recurrence. Solid foundation. What's missing — surface these in your migration, even if you don't build the UI for all of them yet:

- `category` enum: **revenue-generating | non-revenue** (admin / training / maintenance). Drives the AI-first prioritization later.
- `executor_type` enum: **human | ai_agent | robot**. Currently always human; the schema must accommodate the future.
- `skill_required` (FK to a skills table — Step 4.5 detail)
- `cost_code` enum (nullable): **KID | MRD | DOD | SZD | VIZSGALAT** — NDT-specific billing primitives (see Step 4.7 brief below).
- `set_membership` (categories array or junction) — Péter's "halmazok" — tasks can belong to multiple categories simultaneously (e.g., a single task is in "maintenance" + "calibration" + "compliance").
- `status` enum should match Péter's vocabulary: **created (kiírva) → in_progress (folyamatban) → done (elvégezve)** (English fine, just keep the three states mapped).

Don't build the UI for all of this in Step 2 — but **add the columns** so we don't have to migrate the data again in Step 4.5/4.7.

### 3. The CRM is a precondition engine, not just a list
This is the biggest missing piece. Péter doesn't think "task list." He thinks: **"which tasks are currently executable, and what's blocking the rest?"**

Preconditions per task:
- **Person preconditions**: required skill cert exists + cert not expired + medical clearance not expired + person available (not on leave)
- **Equipment preconditions**: equipment present + calibration not expired + consumables not expired
- **Auto-generated upstream tasks**: if a calibration expires in <3 months, the system auto-creates a renewal task assigned to the responsible person.

This becomes its own step (4.5 below). For Step 4 (Deals), just keep the schema open enough that you can FK from `tasks` to `skills` and `equipment` later without pain.

### 4. NDT cost codes are first-class
KID / MRD / DOD / SZD / VIZSGALAT aren't reporting tags — they're the actual billing primitives the live business uses (raw17). The CRM should know:
- A task with cost_code=`SZD` bills the client `personnel_rate × actual_minutes` from arrival-on-site to signed work-log.
- A task with cost_code=`KID` bills travel.
- `DOD` bills per documentation unit.

When the geolocation trigger fires (100m radius from client GPS) on a `SZD` task, the timer starts billing. **This is a Step 4.7 detail** — but the field needs to exist now so future migrations don't churn.

## Step 4 (REWRITTEN) — Fully Customizable Pipelines

Áron's explicit ask. The Step 4 in your current STATUS.md describes a generic kanban. Replace it with this.

### Goal
A user can create N pipelines (NDT sales, Brokerage, Recruitment, Procurement, anything), define stages per pipeline, define custom fields per pipeline, drag deals between stages, save filtered views, and get a "stale deal" red flag when a deal has no open task linked.

### Data model requirements (you design the exact tables)

- **Pipelines** — many per tenant, ordered, with name + optional description + archivable.
- **Stages** — many per pipeline, ordered, each with: name, color, probability_percent (for weighted forecast), optional WIP limit.
- **Deals** — FK to pipeline + stage, position within stage (for drag ordering), value (HUF), company FK, primary person FK, owner, days-in-stage computed.
- **Pipeline custom fields** — per pipeline, user-defined fields: key, label, type (text / number / date / single-select / multi-select / person / company), required Y/N, default value, options JSONB for selects.
- **Deal custom field values** — JSONB column on deal OR a separate value table. Pick one and document the choice.
- **Saved views** — per user, per entity (deal / person / company / task), with filter JSON + sort JSON + column visibility JSON + name + shared (boolean: visible to other tenant members).

### Behavior requirements

- **Drag-drop with optimistic update.** Moving a deal updates `stage_id` + `position_in_stage` + writes an entry to the deal's activity timeline ("Moved from X to Y by Áron, 2026-05-13").
- **Stale-deal warning.** A deal in any non-terminal stage with no open task linked turns red (per Áron — "every active deal must have a next action"). Computed in the query, not stored.
- **Weighted forecast.** Pipeline view shows sum of `deal_value × stage.probability_percent` for non-terminal stages.
- **Multi-pipeline view.** User can see deals across all pipelines they own (e.g., "all my deals over 5M HUF closing this quarter regardless of pipeline").
- **Bulk actions.** Select N deals → change stage / change owner / archive.
- **Universal "+ Deal" quick-create** from anywhere, pre-populated with current context (company page → company auto-filled, etc.). Mirror the universal "+ Task" planned in Step 2.

### Explicitly out of scope for Step 4 (defer)

- **Workflow automation** ("when deal moves to Y, do Z") — Step 6 or later
- **Email integration**
- **Reports / dashboards beyond the weighted forecast number**
- **Mobile responsive** (desktop-first; basic mobile fallback is fine)
- **Per-stage automation rules**

### Modern-CRM features worth absorbing (cite if you use them)

From Pipedrive: universal quick-create, drag-drop kanban, stale-deal warnings, owner-based default views.
From HubSpot: per-pipeline custom fields, deal probability percent on stages, weighted forecast.
From Attio: shared saved views with column visibility config.
From Linear (issue tracker, not CRM): keyboard shortcuts for everything (`c` to create, `g d` to go to deals, etc.) — high-leverage UX investment. Add a `KeyboardShortcuts.md` to `web/docs/` listing them.

### Acceptance for Step 4

- Áron can create a second pipeline ("BirdsView Pilots") with its own stages and custom fields without a code change.
- He can drag a deal between stages and see the activity entry log it.
- He can save a view called "Hot deals — Tier 1 infra" and that view persists across sessions.
- A deal with no open task linked shows red.
- The weighted forecast number changes when stage probabilities are edited.

## Step 6 — Integrations layer + Google Maps + Cost codes + Geolocation (MOVED LATER 2026-05-12)

This was Step 4.7. Áron moved it after Analytics + Ecosystem Hub because nothing time-critical depends on Maps/integrations right now (Lars stores his BirdsView leads locally until Step 5 endpoint exists; the field-visit geolocation trigger is phone-app territory not pressing this quarter).

When this step does run, build the **integrations pattern** with Maps as the first concrete client, so subsequent integrations (Calendar, Resend, Twilio, NAV/SZAMLAZZ) slot in cleanly.

### Architecture pattern

- **`integrations` table** — registered services available to the tenant (id, slug like `google_maps` | `google_calendar` | `twilio`, display_name, status enum `active` | `disabled`, config jsonb)
- **`integration_credentials` table** — encrypted API keys / OAuth tokens, scoped by tenant_id. Use Supabase's `pgsodium` or env-loaded secrets for encryption at rest; never store plaintext keys in the DB.
- **`/lib/integrations/<slug>.ts`** modules — one file per integration, exporting a small typed client (e.g. `googleMaps.geocode(address)`, `googleMaps.distance(origin, dest)`, `googleMaps.directions(...)`)
- **Server-side only.** Integrations never run client-side; they're called from server actions with the tenant context resolved server-side. This protects API keys and gives you usage logging by tenant.
- **Per-call logging.** Every integration call writes a row to `integration_call_log` (tenant_id, integration_slug, method, ms, cost_estimate, success Y/N, timestamp). Cost visibility from day one.
- **Rate-limit / budget caps** at the integration layer — per tenant, per integration, per day. Configurable. Prevents runaway costs.

### Google Maps first — minimum surface

For the geolocation trigger + general CRM use:
- `geocode(address) → { lat, lng, formatted_address, place_id }` — turn HU addresses on companies/persons into coords
- `reverseGeocode(lat, lng) → address`
- `distance(origin, dest) → { meters, seconds }` — used by `KID` (Kiszállási díj) cost-code calculation
- `withinRadius(point, target, meters) → boolean` — used by the field-visit auto-start trigger
- Map widget for company detail page (lazy-loaded; not loaded on list pages)

### Future integrations Áron has flagged (build the pattern such that these slot in)

Áron will name specific tools as needs surface. Likely candidates to anticipate in the pattern (not to build):
- **Google Calendar** — sync deal close dates + tasks to calendar, two-way
