# Performance audit — Helm CRM, 2026-09-07

Owner: Nate. Trigger: Áron — "the speed of the CRM is dogshit"; Vercel flagging INP.

## Method

- **No Vercel Speed Insights data was available for the "before" numbers.**
  `@vercel/speed-insights` was **not installed** at `a34af34` — not in
  `web/package.json`, not in either layout. Whatever INP number was being read off
  the dashboard was not coming from this app's RUM, so field INP could not be pulled
  and the `div.panel-head` attribution could not be reproduced. PR #83 installs it
  (see "Audit: instrumentation" below), so the *next* pass measures instead of infers.
  It still needs enabling on the Vercel project before it reports anything.
- **No connected browser** in this session (`list_connected_browsers` → `[]`), so no
  React Profiler / DevTools trace. Lab INP is therefore *inferred from code*, and
  labelled as such below.
- TTFB: `curl -w %{time_starttransfer}` against **prod** (`ndt-crm.vercel.app`) with a
  real session cookie (`.smoke-auth.mjs`), 4 warm runs per page, **mean** reported.
  Four runs is thin for a platform with variable cold starts — treat the numbers as
  "which continent" resolution, not "which millisecond".
- JS: sum of every `/_next/static/**.js` referenced by the page HTML, fetched
  `--compressed` (decoded bytes).
- Query cost: 5-run mean of the actual SQL against the prod DB from this box.

## Root cause: the functions run in the wrong continent

```
x-vercel-id: fra1::iad1::v54bf-...
```

Edge terminates in Frankfurt, **the function executes in `iad1` (Washington DC)**.
Supabase is `eu-central-1` (Frankfurt). Every Prisma query and every
`supabase.auth.getUser()` is a transatlantic round trip (~95 ms), and the app
issues ~20 of them per page load.

Proof, same commit, same prod database, server running in Budapest (RTT to DB 18.6 ms):

| Page | prod (iad1 → fra) | local prod build (eu → fra) |
|---|---|---|
| `/` | 1.03 s | 0.22 s |
| `/leads` | 1.94 s | 0.39 s |
| `/companies` | 0.91 s | 0.16 s |
| `/persons` | 0.76 s | 0.15 s |
| `/tasks` | 0.84 s | 0.16 s |
| `/deals` | 0.66 s | 0.18 s |

**~5× on the worst page. Geography dominates.**

Caveat on that control, so nobody over-reads it: the local run also has a long-lived
Node process, an already-warm `pg` pool, no Lambda invocation and no cold start. Those
are not separated out. Geography is plainly the dominant term — every SQL statement
returns in exactly the network ping (below) — but "5× from geography *alone*" is
stronger than this experiment supports.

Second-order, and **inside** the number above, not on top of it: `web/src/lib/db.ts`
caps the `pg` pool at `max: 3`. `/leads`' widest phase is 16 concurrent queries
(8 statuses × findMany+count), so they ran in ~6 serialised waves. That cost is
already contained in the 1.94 → 0.39 delta, because the local run had `max: 3` too.
Post-`fra1` the same serialisation costs ~15 ms, not 0.7 s. **So the pool change was
pulled out of PR #82** — it will be re-decided from a measurement taken in `fra1`,
not shipped on a guess. (Vanda, PR #82.)

## What is NOT the problem (measured, so we don't spend on it)

- **Indexes.** Every query in the app returns in *exactly* the network ping
  (18.6 ms ping vs 18.6–24.2 ms per query, 5-run means). Nothing is compute-bound.
  ⚠️ **This conclusion has a shelf life of exactly one deploy.** The 18.6 ms ping is
  the measurement's noise floor, and it hid everything cheaper than ~5 ms. From `fra1`
  the RTT is ~1–2 ms, so a 5 ms query becomes 3× the RTT instead of invisible.
  **Re-measure the same statements from `fra1` before repeating "no indexes needed".**
  The DB is small: 8 161 `company_attributes`, 2 016 `invoices`, 1 703 `companies`,
  1 642 `persons`, 1 080 `contacts`, 675 `interactions`, **8 tasks, 8 lead statuses**.
  Postgres seq-scans 1 700 rows in under a millisecond. On *today's* evidence adding
  indexes buys nothing and costs write amplification. The "~100 k rows" trigger people
  reach for is a guess, not a measurement — the real trigger is the re-measure above.
- **Virtualization.** No list renders >100 rows: `/companies` and `/persons` paginate
  at 30, the closed-leads list at 30, the kanbans cap at 50/column and hold single
  digits of real data.
- **Bundle splitting / `next/dynamic`.** No chunk over 72 KB, 20/22 chunks shared;
  `xlsx` and `@react-pdf/renderer` are already server-only. Nothing worth lazy-loading.
- **`unstable_cache` on reference data.** The reference reads (lead statuses,
  pipeline, users) are single queries returning 8-ish rows. After the region fix
  they cost ~2 ms. Caching them adds an invalidation contract for no gain.
- **A blanket `startTransition` sweep.** It was already in 34 client components. A
  targeted audit (below) found exactly three handlers that had been missed; those are
  fixed. Sweeping the other 34 would have been churn.

| `ImportWizard` | /import only | 377 | It *is* the page | Not applicable |

**Nothing was converted, and that is the finding.** The candidate set — every modal,
dialog, drawer and the palette — is **~2 600 lines total, hand-rolled, with no chart,
editor, or date library behind any of it**. `xlsx` is imported only by
`app/api/import/parse/route.ts` and `@react-pdf/renderer` only by `lib/quotes/pdf.tsx`
— both server-only, verified by grep; neither has ever been in a client bundle.

The measurement that settles it: the largest single chunk on any page is **72 KB**,
20 of a page's 21–22 chunks are the shared shell, and the entire page-specific delta
between `/leads` and `/deals` is **64 KB**. Converting all eleven to
`next/dynamic({ ssr: false })` would move on the order of 10–20 KB per page and buy a
visible open-delay plus eleven new failure modes. Revisit the moment anything here
pulls in a real dependency — a rich-text editor, a chart lib, a PDF viewer — because
that is the case `next/dynamic` exists for, and it is not this codebase today.

`CommandPalette` is the one genuine candidate (it ships on every page and opens on
⌘K). Left anyway: `AppShell` renders it unconditionally with an `open` prop, so
lazy-loading it means switching to a conditional mount, which changes its
mount/unmount semantics. ~8 KB gzipped of ~370 KB is not worth a behaviour change
under a no-behaviour-change brief. Logged as a follow-up.

## Audit: event handlers (Áron's question 2)

| Surface | Handler | Sync work | Verdict |
|---|---|---|---|
| Leads board | `handleDrop`, delete, outcome | `startTransition` already | OK |
| Tasks board | `handleDrop` | `startTransition` already | OK |
| Deals board | `handleDrop`, delete | `startTransition` already | OK |
| Tasks list | `handleReopen`, `handleDelete` | **bare `await action(); router.refresh()`** | **FIXED** — wrapped |
| Task completion (`useTaskCompletion`) | `complete` | `router.refresh()` blocking, modal queued behind it | **FIXED** — refresh deferred |
| Context tasks tab | `handleReopen` | bare await + refresh | **FIXED** — wrapped |
| Company detail | tab switch | renders the whole tab region (~590 lines of JSX, ~300 for the overview body alone) inside the click | **FIXED** — `useDeferredValue` + `inert` |
| Person detail | tab switch | same shape, smaller | **FIXED** — `useDeferredValue` + `inert` |
| Companies filter panel | open / toggle / apply | `useMemo`'d; groups collapsed by default | OK |
| Kanban `onDragOver` | `setHoverCol(key)` | fires at frame rate, but React bails on identical state | OK |
| `DealsKanban:228` | `deals.filter().sort()` per column per render | not memoised | Left — single-digit rows; memoise if the board ever holds hundreds |

`startTransition` was already in 34 client components before this session; **three**
handlers had been missed (Tasks list, context tasks, task completion) and are wrapped.
The two detail-page rows are a different fix — `useDeferredValue`, not a transition.
Honest caveat on the ContextTasksTab one: `await reopenTask()` is network, not
main-thread work, so that wrap is consistency with its siblings more than a measured
INP win.

**On `div.panel-head`:** Áron's guess was the companies filter panel. It is not —
`CompanyFilterBar` renders inside `.page-head`, not `.panel-head`
(`companies/page.tsx:181`). On the five main pages the only interactive children of a
`.panel-head` are the dashboard's four *navigation links* ("Hívás mód →", "Kanban →")
and the company-detail panel buttons. An INP attributed to a `div.panel-head`
containing a `<Link>` is a **navigation** whose next paint waited on the server —
which was 0.7–1.9 s from `iad1`, and is 0.2–0.3 s now.

That points at the real second cause, and it was a gap, not a slow handler:

### Main routes with no `loading.tsx`

`/leads`, `/leads/[id]`, `/tasks/[id]` and `/` (dashboard) had no Suspense boundary,
so clicking a link to any of them painted **nothing** until the server responded — the
interaction stayed open for the whole round trip. Eleven other routes already had one.

Added for **`/leads`, `/leads/[id]` and `/tasks/[id]`**, reusing the existing
`PageSkeleton` components.

**Not for the dashboard.** `app/(app)/page.tsx` has no segment of its own, so its
`loading.tsx` is the whole `(app)` **group** boundary — it would also become the
fallback for the eleven routes below it that have none (`/import`, `/quotes`,
`/automations`, `/marketing`, `/calls`, `/rate-card`, …), painting a KPI-and-chart
skeleton over the quote builder and the import wizard, which today simply hold the old
page. Tried it, Vanda caught it, reverted. Giving the dashboard a boundary needs a
route-group refactor (`(app)/(dashboard)/page.tsx`), which is not a perf change and is
not in this PR.

Known cosmetic, accepted: `/leads/loading.tsx` also covers `/leads?view=closed`, which
is a paginated table, so that secondary view flashes a kanban skeleton. `loading.tsx`
cannot read `searchParams`; splitting the route to fix a ~150 ms flash on the less-used
view is not worth it.

This, not a slow event handler, is the most likely source of the INP warnings.

## Audit: instrumentation (Áron's question 3)

`@vercel/speed-insights` is now in the root layout via `components/Insights.tsx`
(a wrapper, because `beforeSend` is a function and the root layout is a Server
Component). `beforeSend` strips the query string — `/persons?search=…` and the
`/companies` filter params carry customer names, and this is a login-gated CRM.

⚠️ **It reports nothing until Speed Insights is enabled on the Vercel project**
(Project → Speed Insights → Enable). That is Áron's carve-out.

**The after-table above is lab TTFB, not field data.** Once RUM has a few days of
traffic, the next session must redo it from real INP / LCP per route and confirm —
or correct — the `div.panel-head` diagnosis above, which is still an inference.
