# Performance audit — Helm CRM, 2026-09-07

Owner: Nate. Trigger: Áron — "the speed of the CRM is dogshit"; Vercel flagging INP.

## Method

- **No Vercel Speed Insights data.** `@vercel/speed-insights` is **not installed**
  (not in `web/package.json`, not in either layout). Whatever INP number is being
  seen in the dashboard is not coming from this app's RUM, so field INP could not
  be pulled and the `div.panel-head` attribution could not be reproduced. Fixed in
  PR 3 — the package goes in so the next session measures instead of infers.
- **No connected browser** in this session (`list_connected_browsers` → `[]`), so no
  React Profiler / DevTools trace. Lab INP is therefore *inferred from code*, and
  labelled as such below.
- TTFB: `curl -w %{time_starttransfer}` against **prod** (`ndt-crm.vercel.app`) with a
  real session cookie (`.smoke-auth.mjs`), 4 warm runs per page, **mean** reported.
  Four runs is thin for a platform with variable cold starts — treat the numbers as
  "which continent" resolution, not "which millisecond".
- JS: sum of every `/_next/static/**.js` referenced by the page HTML, fetched
  `--compressed` (decoded bytes).
- Query cost: 5-run mean of the actual SQL against the prod DB from this box.

## Root cause: the functions run in the wrong continent

```
x-vercel-id: fra1::iad1::v54bf-...
```

Edge terminates in Frankfurt, **the function executes in `iad1` (Washington DC)**.
Supabase is `eu-central-1` (Frankfurt). Every Prisma query and every
`supabase.auth.getUser()` is a transatlantic round trip (~95 ms), and the app
issues ~20 of them per page load.

Proof, same commit, same prod database, server running in Budapest (RTT to DB 18.6 ms):

| Page | prod (iad1 → fra) | local prod build (eu → fra) |
|---|---|---|
| `/` | 1.03 s | 0.22 s |
| `/leads` | 1.94 s | 0.39 s |
| `/companies` | 0.91 s | 0.16 s |
| `/persons` | 0.76 s | 0.15 s |
| `/tasks` | 0.84 s | 0.16 s |
| `/deals` | 0.66 s | 0.18 s |

**~5× on the worst page. Geography dominates.**

Caveat on that control, so nobody over-reads it: the local run also has a long-lived
Node process, an already-warm `pg` pool, no Lambda invocation and no cold start. Those
are not separated out. Geography is plainly the dominant term — every SQL statement
returns in exactly the network ping (below) — but "5× from geography *alone*" is
stronger than this experiment supports.

Second-order, and **inside** the number above, not on top of it: `web/src/lib/db.ts`
caps the `pg` pool at `max: 3`. `/leads`' widest phase is 16 concurrent queries
(8 statuses × findMany+count), so they ran in ~6 serialised waves. That cost is
already contained in the 1.94 → 0.39 delta, because the local run had `max: 3` too.
Post-`fra1` the same serialisation costs ~15 ms, not 0.7 s. **So the pool change was
pulled out of PR #82** — it will be re-decided from a measurement taken in `fra1`,
not shipped on a guess. (Vanda, PR #82.)

## What is NOT the problem (measured, so we don't spend on it)

- **Indexes.** Every query in the app returns in *exactly* the network ping
  (18.6 ms ping vs 18.6–24.2 ms per query, 5-run means). Nothing is compute-bound.
  ⚠️ **This conclusion has a shelf life of exactly one deploy.** The 18.6 ms ping is
  the measurement's noise floor, and it hid everything cheaper than ~5 ms. From `fra1`
  the RTT is ~1–2 ms, so a 5 ms query becomes 3× the RTT instead of invisible.
  **Re-measure the same statements from `fra1` before repeating "no indexes needed".**
  The DB is small: 8 161 `company_attributes`, 2 016 `invoices`, 1 703 `companies`,
  1 642 `persons`, 1 080 `contacts`, 675 `interactions`, **8 tasks, 8 lead statuses**.
  Postgres seq-scans 1 700 rows in under a millisecond. On *today's* evidence adding
  indexes buys nothing and costs write amplification. The "~100 k rows" trigger people
  reach for is a guess, not a measurement — the real trigger is the re-measure above.
- **Virtualization.** No list renders >100 rows: `/companies` and `/persons` paginate
  at 30, the closed-leads list at 30, the kanbans cap at 50/column and hold single
  digits of real data.
- **Bundle splitting / `next/dynamic`.** No chunk over 72 KB, 20/22 chunks shared;
  `xlsx` and `@react-pdf/renderer` are already server-only. Nothing worth lazy-loading.
- **`unstable_cache` on reference data.** The reference reads (lead statuses,
  pipeline, users) are single queries returning 8-ish rows. After the region fix
  they cost ~2 ms. Caching them adds an invalidation contract for no gain.
- **`startTransition` sweep.** Already present in 34 client components.
