## Method

Lab only. `web/scripts/inp-probe.mjs` — a zero-dependency Node script driving
headless Chrome over CDP (no Playwright/Puppeteer; neither was a dependency and
neither was added).

- Production build (`pnpm`-equivalent `npm run build`), served by `npm run start`
  on `localhost:3100`, real Supabase session cookie via the existing
  `web/.smoke-auth.mjs`.
- **4x CPU throttling** (`Emulation.setCPUThrottlingRate`). Mid-tier hardware is
  the honest baseline for INP; unthrottled desktop numbers would flatter the app.
- Metrics from `PerformanceObserver` `type: 'event'` with `durationThreshold: 0`,
  plus `long-animation-frame` for main-thread attribution.
- **INP is computed only from INP-eligible entries** — `pointerdown`, `pointerup`,
  `click`, `keydown`, `keypress`, `keyup`. This matters: the first version of the
  probe reported `pointerover`/`pointerout`/`pointerleave`, which Event Timing
  records but INP ignores, and those hover entries were shadowing the real clicks
  with 48–64 ms of hover-transition presentation delay. Numbers from that first
  pass were discarded.
- `duration` is decomposed as input delay (`processingStart - startTime`),
  processing (`processingEnd - processingStart`), presentation
  (`startTime + duration - processingEnd`).

Five measurement bugs were found and fixed before the numbers were trusted; each
one silently produced plausible-looking wrong values rather than an error:

1. Headless Chrome only hit-tests the **foregrounded** tab. Without
   `Page.bringToFront`, `elementFromPoint` resolved to `<body>` for every click
   and the dispatch still reported success.
2. Centre-point clicks on a kanban card landed on a nested `<Link>` (company /
   tel), not the card's own `onClick`. Fixed by scanning the card for a point
   that actually resolves to the card itself.
3. A click that starts a client-side SPA navigation races the next
   `Page.navigate`; with under ~2 s of buffer the *following* interaction
   produced zero Event Timing entries despite a successful dispatch.
4. Synthetic `DragEvent`s fired in one tick meant `drop` read a stale, still-null
   `draggingId` — React had not committed between dispatches. Fixed with ~60 ms
   between events.
5. `button[type="submit"]` matched other buttons on the page; the outcome-modal
   submit had to be scoped to `[role="dialog"]`, because base-ui portals dialog
   content out of the card subtree.

Runs mutate the dev database (a lead outcome, and a disposable task created
through the real "Új feladat" flow when the fixture pool is empty). The script
prints a `MUTATED:` line per run.

### Why the single-run numbers above were not trusted

Two runs of the identical warm interactions disagreed by up to 50% (modal submit
88 then 136 ms; tasks completion 32 then 16 ms). Every number was n=1. Since the
headline claim was going to be "under 180 ms", n=1 could not support it — a row
reading 152 ms on one run could read 220 ms on the next.

So the probe grew `--repeat N` (default 7): median / p75 / min / max per row,
rotated interaction order between repetitions to prevent a warm-up effect from
masquerading as a per-interaction difference, every raw sample kept in the JSON,
and automatic flags for `max > 180 ms` and for `spread > median` (too unstable to
conclude from). **The tables below are the ones to read. The single-run numbers
above are kept only to show why repetitions were necessary.**

At N=7 the harness reported **no** unstable rows and **no** repetition-index
drift, so the cold numbers are repeatable app behaviour, not decaying noise.

**This is the finding.** Warm interactions were never the problem and never had
been — `processing` is 0–3 ms on every warm row, which means #83 genuinely
finished the event-handler work. Three of four *cold* rows are over 180 ms **at
the median**, driven entirely by `processing` rising to 67–100 ms: the main
thread is executing the hydration bundle when the click's handler finally runs.
Clicks land 6–12 ms after load in this harness, and that is realistic — SSR'd
HTML looks finished and clickable long before it is hydrated.

## Root cause

LoAF attributes every cold row to one chunk. That chunk is **`react-dom` itself**
(verified by grep: `hydrateRoot`, `Minified React error`, no app strings), so the
cost is React hydrating the tree — it scales with *how much client component tree
each route mounts*, and there is no single fat dependency to lazy-load.

The tree it was hydrating was bigger than it needed to be. `components/layout/Topbar.tsx`
sits in the app shell on **every route** and statically imported `TaskModal`
(314 lines) and `DealModal` (205 lines), which in turn pull in `EntitySearch`,
`Select`, `Textarea`, `FormField`, `lib/tasks/costing` and two server actions.
All of it had to download and parse before hydration could complete on every
single page — so that the "+" menu could open a modal the user may never touch.

## What shipped

1. **`Topbar`: `TaskModal` + `DealModal` behind `next/dynamic({ ssr: false })`,
   mounted on first open.** A mount latch (`taskMounted` / `dealMounted`) keeps
   each modal mounted once opened, so a half-filled form still survives a close
   and reopen exactly as before — gating purely on the `open` flag would have
   deferred the chunk too, but would silently have started wiping user input.
   Both open paths route through a single `openTask()` / `openDeal()` so a future
   call site cannot open a modal without mounting it.
2. **`components/ui/dialog.tsx`: dropped `backdrop-blur` and the `duration-100`
   enter/exit animations** from the overlay and popup. `backdrop-filter` forces a
   full-viewport composite on every dialog open, and a 100 ms enter animation held
   the interaction open for its own duration — together worth ~32 ms of the
   104 ms warm median on "leads: outcome modal open" (104 → 72 ms, N=7). This also
   brings the dialog back in line with Áron's own Phase 1.5 constraint, *"No
   glass, gradients, or animations."*

### Caveats, so nobody over-reads this

- **The two changes were measured together, not separately.** They are separable
  by inspection — the cold rows moved because of the dynamic imports, the warm
  modal rows because of the dialog change — but I did not run an isolating build
  for each. If one has to be reverted, re-measure rather than assuming the split.
- `tasks: completion click` (warm) is flagged **UNSTABLE** after the change:
  median 16 ms but max 48 ms, a spread wider than its own median. Every value is
  far under budget so it does not block anything, but the row is too noisy to
  claim an improvement from.
- `companies: filter typing` (warm) went 56 → 64 ms median. Within run-to-run
  noise for that row (min 40, max 72) and not treated as a regression.
- `leads: card drag` reports **0/7 samples in both runs**. The synthetic
  `DragEvent` path is not Event Timing, and warm/idle drag produced no LoAF
  entries at all — it is too cheap to register. **This interaction is unmeasured,
  not measured-and-fast.** Do not quote a drag number from this document.
- Fast-3G + 4x CPU is a deliberately pessimistic profile. Real numbers on Áron's
  desktop will be better; real numbers on a mid-range phone on Hungarian mobile
  may be worse.

## The cost of the fix, measured — first open of the two Topbar modals

Vanda (PR #86) caught that the one interaction this change makes *slower* was the
one interaction missing from every table above: the first open of the shell
modals now waits on a network fetch. She was right, so it was measured.

Timed **inside the page** with a `MutationObserver` (click dispatch → the
`[role="dialog"]` node existing), so the number contains no CDP polling overhead.
Same pessimistic profile: fast-3G, 4x CPU, cold cache, 3 runs each.

| first open of a modal | time to dialog |
|---|---|
| **control** — `/tasks` "Új feladat" (still a static import) | 223 / 235 / 242 ms |
| **Topbar "Feladat"** (now `next/dynamic`) | 486 / 497 / 507 ms |

**≈260 ms of real regression on first open**, once per session per modal, on a
deliberately harsh network. Two mitigations are in, one attempt was rejected:

- `onMouseEnter` / `onFocus` on both buttons mount ahead of the click. Measured
  546–624 ms → **237–332 ms** with a 400 ms hover dwell. Pointer and keyboard
  users mostly stop paying the cost; touch users have no hover, which is why the
  click path still latches on its own.
- A post-hydration `useEffect` mounts both modals after the hydration commit, so
  the chunk fetch starts immediately instead of on demand while still costing the
  hydration window nothing.
- **`requestIdleCallback` was tried first and measured *worse* (683 ms).** It
  defers past the point a real user clicks. Removed rather than kept on theory.

**The trade, stated plainly so it can be overruled:** a 216 ms median improvement
on opening a lead card — the highest-frequency interaction in the CRM — against
≈260 ms once per session on two "+" buttons, on a network profile worse than
Áron's. That is worth it on these numbers. It would not be if the modals were
opened constantly, and it is not free.

**Follow-up, not done here:** the button has no loading affordance during that
fetch. A visible pending state on first open would remove the "dead button" feel
without touching the INP win. Worth a small PR; out of scope for an INP sprint.

## Corrections to `docs/PERF_2026-09-07.md`

- **The `div.panel-head` diagnosis was wrong, and so was Áron's original guess.**
  The 09-07 doc inferred these were navigations waiting on a slow server. Measured,
  the dashboard `.panel-head` nav link is the *fastest* interaction on the board
  warm (16 ms, `processing` 1 ms). It was over budget only cold (200 ms), and the
  cause is hydration, not the handler and not the server round trip. The original
  Phase 1.5 note — "`div.panel-head` click handler blocks UI ~200ms (likely the
  companies filter panel)" — named roughly the right number for the wrong reason.
- **The lazy-loading audit's conclusion was right on its evidence and wrong overall.**
  09-07 declined every `next/dynamic` conversion because no chunk exceeded 72 KB and
  the modals were hand-rolled with no heavy dependency. That reasoning only holds
  warm. It missed that two of those modals sat in the *shell*, on every route, where
  the cost is not chunk size but hydration work blocking the first click. The audit
  measured the right thing and asked the wrong question of it.
