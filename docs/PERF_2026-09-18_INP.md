# INP measurement - NDT CRM, 2026-09-18

Owner: Nate. Ticket: NDT-INP-2. Trigger: finish the INP measurement report a previous
attempt never finished. **Measurement only** - no application code was changed. The
only files touched were this report and `web/scripts/inp-probe.mjs` (two fixes, both
required to get any trustworthy number at all, detailed below).

## Environment incident, found and fixed before any number was trusted

The first full run (started against what looked like a clean local build) turned out
to be contaminated. `ps` showed a second `inp-probe.mjs` process still alive from
roughly 13 hours earlier (started 2026-09-17 23:50, almost certainly the "previous
attempt" this ticket exists to finish) that had never exited. `inp-probe.mjs` hardcodes
`CDP_PORT = 9333` for the Chrome DevTools Protocol connection. That stale process's
Chrome instance had the IPv4 side of `127.0.0.1:9333` already bound; my freshly spawned
Chrome only managed to bind the IPv6 side of the same port number. The probe's own
`pollForVersion()` fetches `http://127.0.0.1:9333/json/version` - IPv4 literal - so
every run I started, including the sanity checks used to validate the new selectors,
was silently attaching to and driving the **13-hour-old Chrome instance**, not the one
it had just spawned for itself. Two independent Node processes were then issuing CDP
commands (including `Page.bringToFront`, which headless Chrome's hit-testing depends
on) against the same browser concurrently.

Fix: killed both process trees (`kill -9` on both `inp-probe.mjs` PIDs and both Chrome
trees, matched by `user-data-dir`), confirmed `ss -ltnp | grep 9333` showed nothing
before restarting, then confirmed a fresh run showed exactly one process owning
`127.0.0.1:9333` before letting it run to completion. The contaminated first run never
produced a results table or JSON (it was killed mid-way through its first warm
interaction) - there is no contaminated data to discard, only a clean run to report.
**Every number below comes from that single, uncontended run.**

## Method (unchanged from `docs/PERF_2026-09-08_INP.md`)

- `web/scripts/inp-probe.mjs` - zero-dependency Node script driving headless Chrome
 over CDP (no Playwright/Puppeteer).
- Local production build (`npm run build`), served by `next start -p 3100`, against the
 **local fixture Postgres** (`ndtcrm-fixture-db`, `127.0.0.1:5439`) - never production,
 never `web/.env`. Session cookie from the existing `web/.smoke-cookie.txt`.
- **4x CPU throttling** (`Emulation.setCPUThrottlingRate`).
- Metrics from `PerformanceObserver` `type: 'event'` (`durationThreshold: 0`) plus
 `long-animation-frame` for main-thread attribution. INP computed only from
 INP-eligible entries (click/tap/keyboard), never hover.
- **Warm**: idle, hydrated, unthrottled network, settled ~800ms after load.
- **Cold**: fresh navigation every repetition, cache cleared, fast-3G-ish network
 (150ms latency, 1.6Mbps down), clicked the instant the target is hit-testable - not
 after an artificial settle. This is the hydration window.
- **N=7 repetitions per interaction, rotated order between reps.** Median / p75 / min /
 max reported, plus automatic flags for `max > 180ms` and for spread exceeding the
 median (`UNSTABLE`) - both carried over unchanged from the 09-08 methodology.

## Which interactions breach the 200 ms / 500 ms lines

The probe's own `computeStats()` already treats the run's **max**, not the median, as
the number that decides "over budget" (`overMax180: max > 180` - its own comment:
"INP is a high-percentile metric - max is the number that matters, never dropped as
noise"). Applying that same logic to the ticket's 200/500 lines:

**No interaction breaches 200 ms on its median.** The closest is `marketing board:
bulk-select checkbox` (cold) at median 184 ms.

**Over 200 ms on max (needs improvement), all cold:**
dashboard nav link (264), kanban card open (456), tasks completion (216), marketing
board list toggle (288), marketing board bulk-select checkbox (344), marketing/[id]
edit box open (784), outreach copy button (352).

**Over 500 ms on max (poor):** only `marketing/[id]: edit box open` (cold), one
repetition at 784 ms; its other six repetitions were 160-200 ms.

## Where the time goes (from the probe's decomposition, not speculation)

For every cold row above, `inputDelayMs` stays low (1-35 ms) and `presentationMs` is
modest (14-138 ms). The dominant term is `processingMs`, backed by matching
`worstLoafBlockingMs`, and the long-animation-frame's script attribution is
consistently `.next/static/chunks/17mubwtqwijpu.js`. I grepped that chunk directly
rather than infer from the filename: it contains `hydrateRoot`, `createRoot` and the
string `react-dom`, and no app-specific component names (no `TaskModal`, `DealModal`,
`Topbar`). This is the same root cause the 2026-09-08 report already established - the
cost is React hydrating the mounted client component tree, not a single prunable
dependency. Concretely:

- **dashboard nav link cold** (median 96, worst rep 264): processing 0-159 ms.
- **kanban card open cold** (median 104, worst rep 456): processing 89-360 ms - the
 worst normal-range row, and worse than the 96 ms this same interaction measured at
 after the 09-08 fix (see caveats).
- **marketing board list toggle cold** (median 160): processing 92-183 ms on every one
 of the 7 reps, not just the outlier - this row's whole distribution sits near the
 200 ms line.
- **marketing board bulk-select checkbox cold** (median 184): the only row whose
 median itself is within 20 ms of the 200 ms line.
- **marketing/[id] verdict button cold** (median 176) and **edit box open cold**
 (median 176, one rep 784): processing 109-135 ms baseline across 6 of 7 reps; the
 784 ms rep alone had processing=650 ms / loafBlocking=736 ms with **no named script**
 in its attribution - an anomaly, not representative of the other six reps (see
 caveats).
- **outreach copy button cold** (median 80, one rep 352): baseline processing 0-60 ms;
 the 352 ms rep alone had processing=303 ms.

## Caveats, so nobody over-reads this

1. **Environment incident** (above) - the first run was contaminated by a 13-hour-old
 stray process squatting the CDP port and was discarded before producing any table.
 Only the clean re-run is reported.
2. **The last cold repetition was anomalously slow on almost every row.** Repetition 7
 (after rotation) was 2-4x its own row's other-repetition average on 7 of 14 cold
 rows (264 vs ~90 ms baseline; 456 vs ~103 ms; 784 vs ~172 ms; 352 vs ~64 ms), and
 this shows up simultaneously across unrelated pages (dashboard, tasks, marketing,
 outreach), which points toward a single shared cause - most plausibly memory/GC
 pressure accumulating in the one long-lived headless Chrome process across the
 full run's 98 cold navigations, rather than something specific to any one page's
 data. **Not diagnosed further here** - flagged, not concluded, per the
 measure-don't-optimize mandate. A rerun with a fresh Chrome process per cold
 repetition (a probe-methodology change, not an app fix) would settle whether this
 is measurement artifact or a real degradation under memory pressure.
3. **Sample count**: several rows fell short of 7/7 successful samples despite 7
 attempts each - `outreach: copy button` (warm) 4/7, `drive: outcome button` (warm)
 5/7, `drive: note textarea typing` (warm) **1/7**, `dashboard nav link` (warm) 6/7,
 `tasks completion` (warm) 6/7, `"Rám vár" toggle` (warm) 6/7. Every miss was "no
 Event Timing entries captured at all" on an isolated single repetition scattered
 through the run (not clustered at the end, not the checklist/copy-button-specific
 pattern) - consistent with the known flakiness of very fast (<=24 ms) interactions
 occasionally not firing an observable event, already present in the 09-08
 methodology. The surviving samples in each row are internally consistent (spreads
 of 0-16 ms), so the median is trustworthy for all of them **except**
 `drive: note textarea typing`, which has exactly one successful sample and should
 be treated as **unmeasured**, not "measured at 16 ms."
4. **`marketing/[id]: checklist panel toggle` is unmeasured (0/7 both warm and cold),
 and this is a fixture-data gap, not a probe bug.** `content_checks` has zero rows
 for any content item in the fixture DB (`select count(*) from content_checks` = 0),
 so there is no resolve/waive control anywhere in the fixture data to click.
 `content-fixtures.mjs` does not currently seed this table. Do not quote a number for
 this interaction.
5. **Possible regression, not confirmed**: `leads: kanban card open` (cold) measured
 96 ms median in the 09-08 "after" table; this run measured 104 ms median and 168 ms
 p75, both worse. Given caveat 2 (whole-run drift affecting this exact row's worst
 rep) and caveat 1 (the first attempt was contaminated and discarded), I would not
 call this a confirmed regression without a repeat run on an otherwise-idle machine -
 but the direction is the one a regression would show. Flagging for Nate rather than
 concluding.
6. Fast-3G + 4x CPU is a deliberately pessimistic profile, same as 09-08. Real numbers
 on better hardware/network will be better.

## Proposed fixes - not implemented

1. **Audit each of the four required screens for client-component surface area that
 can move to the server or behind `next/dynamic`, the same pattern that already
 worked on `Topbar`'s `TaskModal`/`DealModal` in the 09-08 sprint.** The evidence
 here (react-dom itself dominating every cold row's processing time, not an
 app-specific chunk) says there is no single dependency left to trim - the next win
 has to come from mounting less client-tree per route. Expected win: bringing
 `marketing board: bulk-select checkbox` (184 ms median, closest to breaching 200)
 and `marketing board: list toggle` (160 ms median, processing 92-183 ms on every
 rep) down the same way the 09-08 sprint took kanban-card-open cold from 312 ms to
 96 ms. Risk: same trade as before - anything deferred costs its first-open latency
 once per session; needs the same "measure the cost, not just the win" treatment the
 09-08 report gave the Topbar change.
2. **Seed `content_checks` fixture rows** (extend `content-fixtures.mjs` with a
 `--checks=N` flag analogous to `--pipeline`/`--live`) so `checklist panel toggle` -
 one of the ticket's four required interactions - is actually measurable next time,
 instead of a permanent 0/7. No INP win by itself; closes a real blind spot. Risk:
 essentially none, it only touches fixture-seeding tooling.
3. **Re-run the cold pass with a fresh headless Chrome process per repetition**
 (currently one Chrome serves all 98 cold navigations in a run) to determine whether
 the last-repetition 2-4x slowdown (caveat 2) is a measurement artifact or a real
 effect. This gates confidence in the two biggest numbers in this report (784 ms and
 456 ms) - right now neither should be treated as a stable characteristic of the app
 until that ambiguity is resolved. No app risk, this is a probe change only.
